# 機能仕様書: deepinfer-spec-tuner

- 版: 0.1（ドラフト）
- 対象: DeepInfer `main` @ `5537415`
- 以下で `file:line` と書く箇所は、すべて DeepInfer リポジトリ内のパスを指す。

## 1. 目的

投機デコードの設定を、利用者自身のワークロードで実測して決められるようにする。対象は次の 3 つ。

| 設定 | 定義箇所 | 内容 |
|---|---|---|
| `DEEPINFER_USE_NEXTN_DECODE` | `environ.py:136` | 投機トークンの最大数。既定 5、0 で無効 |
| `DEEPINFER_DFLASH_CONFIDENCE_HEAD_TEMPERATURE` | `environ.py:142-150` | スカラー、または nextn 個の位置別の値。`models/mtp/dflash.py:62-64` で使われる |
| `DEEPINFER_ENABLE_MTP_VARLEN` | `environ.py:138` | confidence に基づく可変長の検証 |

## 2. 背景（既存の道具との違い）

| 既存 | 問題 |
|---|---|
| `examples/benchmark.py:396-409` | 全受理を前提に `avg_sps × bs × (1 + nextn)` を出す。プロンプトもランダムなトークン列（`benchmark.py:299`）なので、受理率を測っても実ワークロードの値にならない |
| `examples/sweep/plot_pareto.py:58-61` | 受理率は人が入力する仮定値 |
| `stats_logger.py:211-236` | 実測の受理率を計算しているが、テキストログに出すだけで、スループットの評価に使われていない |

**設計上の重要な判断:** 本ツールは `benchmark.py` を呼ばない。利用者のプロンプトを `deepinfer.LLM.generate` に流す独自のドライバを持つ。

## 3. スコープ

### 対象

- nextn × 温度（スカラー）のグリッドスイープ。各点はエンジンを起動し直して計測する。
- 実効スループット、実測受理率、TPOT の算出と、構成の推薦。
- 位置別の温度（カンマ区切りのタプル）は、明示的に指定された候補だけを評価する。組み合わせの自動探索はしない。

### 対象外（v0.1）

- `MTP_VARLEN=1` を推薦の対象に含めること。計測と表示はするが、「参考値」として扱う（9 章）。
- オンライン（本番トラフィック）での継続的な調整。
- マルチノード構成の自動起動。単一ノード内の DP / EP は、DeepInfer の既存ランチャ（`examples/_launch.py`）を使う。

## 4. 入力

### 4.1 ワークロードファイル（JSONL）

```json
{"prompt": "...", "max_tokens": 1024}
{"prompt_token_ids": [1, 2, 3], "max_tokens": 512, "temperature": 0.6}
```

- `prompt` か `prompt_token_ids` のどちらか一方は必須。
- サンプリングのパラメータは、行ごとに上書きできる。既定値は CLI で与える。
- 受理率は出力の分布に依存する。そのため、本番に近いサンプリング設定（温度・top-p）で測ることを README で推奨する。

### 4.2 CLI

| 引数 | 既定 | 説明 |
|---|---|---|
| `--model` | 必須 | |
| `--prompts FILE` | 必須 | 4.1 の JSONL |
| `--nextn N...` | `0 3 5` | 0 は比較用のベースライン（投機なし） |
| `--temperature T...` | `1.0` | confidence head の温度。`"1.2,1.1,1.0"` の形でタプルも指定できる |
| `--varlen {off,on,both}` | `off` | |
| `--ep`, `--dp` | 環境から | DeepInfer の起動規約に従う |
| `--warmup-requests` | 32 | 計測から除外する先頭のリクエスト数 |
| `--repeats` | 1 | 各点の繰り返し回数。2 以上なら平均とばらつきを出す |
| `--out DIR` | 必須 | 結果の保存先。再開に使う |
| `--slo-tpot-ms` | なし | 指定すると、TPOT がこの値以下の点だけを推薦の対象にする |

入力の検証（エンジンを起動する前に行う）:

- タプル形式の温度の要素数が、組み合わせる nextn と一致しない場合はエラーにする（本体の `environ.py:146-149` と同じ規則）。
- `nextn=0` と温度を組み合わせた点は、温度が無意味なので 1 点にまとめる。

## 5. 処理

### 5.1 1 点の計測手順

1. 子プロセスを起動し、環境変数 `DEEPINFER_USE_NEXTN_DECODE`、`..._TEMPERATURE`、`..._ENABLE_MTP_VARLEN` を設定する。env はプロセス起動時に確定するので、点ごとにプロセスを分ける。
2. 子プロセスで `LLM(model, ..., disable_log_stats=False)` を作る。`LLM` は既定でログを止めている（`entrypoints/llm.py:66`）ので、明示的に有効化する。あわせて `DEEPINFER_LOGGING_INTERVAL_STEP` を小さく（既定 10）設定する。
3. ウォームアップ用のリクエストを `generate` に流し、その結果は捨てる。
4. 計測対象の全リクエストを 1 回の `generate` で投入し、壁時計で計測する。
5. 結果から、生成トークン数の合計と、リクエストごとの完了時刻を集める。
6. stdout / stderr を保存し、8 章のパーサで統計行を抽出する。

### 5.2 算出する指標

| 指標 | 定義 | 出所 |
|---|---|---|
| `output_tok_s_per_gpu` | 生成トークン数の合計 ÷ 計測時間 ÷ GPU 数 | 実測（主指標） |
| `accept_rate[i]` | 位置 i の受理率 | 統計ログの `nextn_accept_rate [...]`（`stats_logger.py:305`） |
| `avg_accept_rate` | | 同 `avg_nextn_accept_rate`（`:304`） |
| `avg_verified_len` | | 同（`:308`） |
| `avg_confidence_error` | | 同（`:309`） |
| `tpot_ms` | 計測時間 ÷ リクエストあたりの平均出力長（近似） | 実測 |
| `speedup` | `output_tok_s_per_gpu` を `nextn=0` の値で割ったもの | 導出 |

主指標は、ログから導出した値ではなく、実際に生成されたトークン数とする。こうすれば VARLEN の on / off に関係なく、同じ定義で比較できる。

### 5.3 ログの集計

- 統計行は、ランクごとに `RANK n, GPU g, step s, [stats] (k v | ...)` という形式で出る（`stats_logger.py:287`）。
- 計測区間に入る行だけを使う。step 番号でウォームアップ区間を除く。
- 受理率は区間内の値の平均ではなく、`accepted_tokens` と `verified_tokens` の累積から算出し直す。窓の平均を平均すると偏るため。

### 5.4 推薦

- SLO の条件を満たす点のうち、`output_tok_s_per_gpu` が最大のものを推薦する。
- `--repeats` が 2 以上のときは、1 位と 2 位の差が繰り返し間のばらつき（標準偏差の 2 倍）より小さい場合、「有意差なし」と表示する。

## 6. 出力

`--out DIR` に次のファイルを置く。

- `points/<id>/stdout.log`: 生のログ
- `points/<id>/result.json`: 5.2 の指標と、その点の構成
- `summary.csv`: 全点の一覧
- `report.md`: 指標の表、推薦、位置別受理率の表

既に `result.json` がある点はスキップする（再開に対応）。

## 7. 非機能要件

- 1 点が失敗（エンジンの異常終了・タイムアウト）しても、残りの点は続ける。失敗した点は `summary.csv` に `status=failed` と記録する。
- ログのパーサは、DeepInfer のコードを import せずに動くこと。GPU のない環境でも、過去の結果を再集計できるようにするため。

## 8. ログパーサ

- 1 行を `RANK (\d+), GPU (\d+), step (\d+), \[(\w+)\] \((.*)\)` で分解する。
- 本体の `( ... )` 部分を ` | ` で区切り、各項目を「最初の空白より前がキー、後ろが値」として取り出す。
- 値が `[a%, b%, ...]` の形ならリストとして解釈する。
- 未知のキーは保持し、知らないキーがあってもエラーにしない。
- 書式に互換性のない変更があったことを検知するため、`stats_logger.py:298-327` の f-string から作った固定のサンプル行で回帰テストを行う。

## 9. 未決事項とリスク

- **VARLEN=1 の扱い:** `plot_pareto.py:59` の assert から、「VARLEN=1 では SPS に受理率が既に含まれる」という設計意図が読み取れる。本ツールは主指標を実測のトークン数にしているので、二重計上は起きない。ただし、推薦に入れる前に VARLEN=0 との比較を実機で 1 回行い、受理率の定義をそろえる必要がある。
- **ログ間隔を変えることの副作用:** `DEEPINFER_LOGGING_INTERVAL_STEP` を小さくしたときに、統計の窓の挙動が変わらないかは未検証。間隔を 10 と 100 にした 2 回の測定で、受理率が一致することを実機で確かめる。
- **ワークロードの代表性:** 受理率はプロンプトの分布とサンプリング温度に強く依存する。少量のプロンプトでは結論が不安定になる可能性がある（推測）。そのため v0.1 では、推奨する最小件数（例: 256 リクエスト）を README に書く。
- **計測時間:** 各点でモデルを読み込み直すので、1 点あたりの起動コストが大きい。`--repeats` は既定を 1 とし、上位の候補だけを再計測する 2 段階モードは今後の検討とする。
